# سامانه انبار قطعات (QR + PWA فارسی)

سامانه‌ای برای ثبت ورود و خروج قطعات انبار با اسکن QR، تایید خروج‌ها توسط مدیر، نگهداری کامل تاریخچه، و خروجی Excel کامل و خروجی مخصوص سپیدار.

## راه‌اندازی

### ۱) اجرای محلی (بدون داکر)

پیش‌نیاز: Node.js نسخه ۲۲.۱۳ یا بالاتر.

```bash
make install && make run        # یا: npm install && npm start  (روی ویندوز: start.bat)
```

سپس `http://localhost:3000` را باز کنید. داده‌ها در پوشه‌ی `data/` ذخیره می‌شود.

### ۲) داکر روی کامپیوتر خودتان (برای آزمایش)

```bash
make images        # ساخت image (حدود یک دقیقه)
cp .env.prod.example .env.prod
make up-prebuilt   # اجرا روی http://localhost:8090 (پورت از HTTP_PORT در .env.prod)
make health        # بررسی سلامت
make smoke         # تست سرتاسری (فقط‌خواندنی)
```

### ۳) استقرار روی سرور (Ubuntu/Debian) — یک دستور

پروژه را روی سرور کپی کنید (git clone یا scp) و:

```bash
DOMAIN=warehouse.example.com LETSENCRYPT_EMAIL=you@example.com ./scripts/bootstrap-vps.sh
```

این اسکریپت داکر را نصب می‌کند، `.env.prod` می‌سازد، image را می‌سازد، برنامه را بالا می‌آورد، nginx و گواهی Let's Encrypt را تنظیم می‌کند و در پایان نام‌کاربری و گذرواژه‌های اولیه را نشان می‌دهد. نکات:

- **چند پروژه روی یک سرور:** nginx سرور مشترک است؛ فقط یک vhost مخصوص همین دامنه اضافه می‌شود و پورت محلی آزاد خودکار انتخاب می‌شود.
- **سرور ضعیف (۱ گیگ رم):** image را روی کامپیوتر خودتان بسازید و بفرستید:
  ```bash
  ./scripts/build-images.sh                       # روی کامپیوتر شما → dist/warehouse-image.tar.gz (حدود ۸۵ مگابایت)
  scp dist/warehouse-image.tar.gz root@SERVER:/opt/warehouse/
  # روی سرور:
  ./scripts/load-images.sh && ./scripts/bootstrap-vps.sh
  ```
  برای معماری ARM: `PLATFORM=linux/arm64 ./scripts/build-images.sh`.
- **فقط شبکه‌ی داخلی (بدون دامنه):** `LAN_ONLY=1 ./scripts/bootstrap-vps.sh` — توجه: بدون HTTPS دوربین گوشی کار نمی‌کند.
- **به‌روزرسانی:** پروژه‌ی جدید را کپی کنید و `make prod-up` (یا image جدید را `load-images` و `make up-prebuilt`). داده‌ها در volume به نام `warehouse-data` می‌ماند.

### دستورهای روزمره

| دستور | کار |
|---|---|
| `make prod-ps` / `make prod-logs` | وضعیت و لاگ |
| `make health` / `make deploy-health HOST=https://…` | بررسی سلامت |
| `make smoke SMOKE_USER=… SMOKE_PASSWORD=…` | تست سرتاسری فقط‌خواندنی |
| `make prod-credentials` / `make prod-clear-credentials` | نمایش / حذف گذرواژه‌های اولیه |
| `make prod-shell CMD="reset-password mokhtar"` | بازنشانی گذرواژه (یا `list-users`, `create-admin`, `stats`) |
| `make prod-shell CMD="set-super abolfazl"` | «مدیر ارشد» کردن یک مدیر (حساب نباشد: اول `create-admin abolfazl "ابوالفضل"`) |
| `make backup` / `make restore FILE=backups/…db` | پشتیبان‌گیری و بازیابی |
| `make deploy-check` | بررسی پیش از استقرار |
| `make demo-data API_URL=… ADMIN_USER=… ADMIN_PASSWORD=…` | داده‌ی آزمایشی (فقط روی انبار خالی) |

**پشتیبان‌گیری خودکار:** برنامه خودش هر روز (به‌طور پیش‌فرض بعد از ساعت ۲ بامداد) از پایگاه داده پشتیبان می‌گیرد، سلامت فایل را بررسی می‌کند و ۱۴ فایل آخر را در `/data/backups` (داخل volume) نگه می‌دارد. تنظیم و دریافت فایل‌ها: «تنظیمات › پشتیبان‌گیری خودکار». `make health` اگر آخرین پشتیبان قدیمی‌تر از دو روز باشد هشدار می‌دهد.

بازگردانی یک پشتیبان: فایل را از تنظیمات دریافت کنید (یا `docker cp warehouse-app:/data/backups/<file> backups/`) و سپس `make restore FILE=backups/<file>`.

کپی روی خودِ سرور، بیرون از volume (اختیاری، cron): `30 2 * * * cd /opt/warehouse && ./scripts/backup-prod.sh >> backups/backup.log 2>&1`

### نسخه و به‌روزرسانی از داخل برنامه (آزمایشی)

- نسخه‌ی در حال اجرا (شماره‌ی نسخه و commit) پایین صفحه‌ی «بیشتر» و در «تنظیمات › نسخه و به‌روزرسانی» دیده می‌شود. `/health` هم آن را برمی‌گرداند.
- برنامه داخل کانتینر است و خودش نمی‌تواند خودش را بازسازی کند؛ برای همین یک سرویس کوچک روی سرور این کار را انجام می‌دهد. یک بار روی سرور بزنید: `make updater-install` (حذف: `make updater-uninstall`، وضعیت: `make updater-status`، لاگ: `make updater-logs`).
- بعد از آن مدیر سیستم در تنظیمات می‌تواند «بررسی نسخه جدید»، «به‌روزرسانی» و «بازگشت به نسخه‌ی قبلی» را بزند.
  - **به‌روزرسانی:** پشتیبان پایگاه داده ← `git pull` (فقط fast-forward از شاخه‌ی `main`) ← `make prod-up` ← بررسی سلامت. اگر نسخه‌ی جدید بالا نیاید، نسخه‌ی قبلی خودکار برمی‌گردد.
  - **بازگشت:** کد به نسخه‌ای که قبل از آخرین به‌روزرسانی اجرا می‌شد برمی‌گردد. داده‌ها (قطعات، اسناد، موجودی) دست نمی‌خورند.
- اگر روی سرور فایل‌های ردیابی‌شده را دستی تغییر داده باشید، به‌روزرسانی خودکار انجام نمی‌شود (پیام می‌دهد). روش دستی همیشه کار می‌کند: `git pull && make prod-up`.

### مدیر ارشد

- «مدیر ارشد» در «بیشتر › کاربران» برای هر کاربر (انباردار یا مدیر دیگر، و خودش) با «تعیین گذرواژه» گذرواژه‌ی دلخواه می‌گذارد؛ کاربر از همه‌ی دستگاه‌ها خارج می‌شود. می‌توان تعیین کرد که در ورود بعدی گذرواژه را عوض کند.
- وقتی مدیر ارشد وجود دارد، مدیرهای دیگر فقط حساب انباردارها و خودشان را تغییر می‌دهند؛ حساب و گذرواژه‌ی مدیرهای دیگر فقط دست مدیر ارشد است. مدیر ارشد را نمی‌توان از داخل برنامه غیرفعال یا تنزل داد.
- مدیر ارشد فقط از خط فرمان سرور تعیین می‌شود (`set-super` / `unset-super`). حسابی با نام کاربری `abolfazl` اگر مدیر باشد، خودکار مدیر ارشد می‌شود.

### اولین ورود

- ۱۱۴ قلم (از ۹۳ قطعه‌ی فایل Word، هر حالت یک قلم مستقل با QR مستقل) با عکس‌هایشان وارد می‌شود. موجودی همه صفر است.
- سه حساب ساخته می‌شود: `mokhtar` و `sattar` (مدیر سیستم) و `anbardar` (انباردار) با گذرواژه‌ی تصادفی (در لاگ و در `/data/FIRST-RUN-PASSWORDS.txt` داخل volume). در اولین ورود تغییر گذرواژه اجباری است؛ پس از یادداشت‌کردن `make prod-clear-credentials` را بزنید.
- موجودی اولیه را مدیر ثبت می‌کند: از صفحه‌ی اسکن با علت «موجودی اولیه»، یا از صفحه‌ی هر قطعه › «اصلاح موجودی (شمارش)»، یا با ستون «موجودی اولیه» در فایل اکسل ورود قطعات.

## نقش‌ها و گردش کار

| | مدیر سیستم | انباردار |
|---|---|---|
| اسکن و ثبت ورود | مستقیم اعمال می‌شود | مستقیم اعمال می‌شود (قابل تغییر در تنظیمات) |
| ثبت خروج (تحویل به کارگر، ضایعات…) | مستقیم اعمال می‌شود | **به صورت درخواست ثبت می‌شود و پس از تایید مدیر اعمال می‌شود** |
| تایید / رد درخواست‌ها | ✔ | ✘ |
| افزودن و ویرایش قطعه، چاپ برچسب، اصلاح موجودی | ✔ | ✘ |
| گزارش‌ها، خروجی‌ها، کاربران، تنظیمات، ممیزی | ✔ | ✘ |

- انباردار فهرست قطعات را اسکن می‌کند، تعداد و توضیح هر ردیف را می‌نویسد، نام کارگر را وارد می‌کند و «ارسال برای تایید» را می‌زند. موجودی تا تایید مدیر **تغییر نمی‌کند**.
- مدیر در صفحه‌ی «درخواست‌ها» (با نشانگر تعداد) تایید یا با ذکر دلیل رد می‌کند. موجودی هنگام تایید دوباره کنترل می‌شود و (تا وقتی گزینه‌ی «کنترل موجودی» در تنظیمات روشن است) هرگز منفی نمی‌شود. با خاموش کردن آن در «تنظیمات»، ثبت خروج بیش از موجودی هم ممکن است و موجودی می‌تواند منفی شود.
- هر سند، هر ردیف (با موجودی قبل و بعد)، ثبت‌کننده، تاییدکننده و زمان‌ها برای همیشه ذخیره می‌ماند؛ حذف سند در سطح پایگاه‌داده ممکن نیست. رد و لغو هم ثبت می‌شود. سایر تغییرات (ویرایش قطعه، کاربران، ورود، خروجی‌ها) در «گزارش ممیزی» می‌آید.
- تاریخ‌ها شمسی و به وقت تهران هستند.

## برچسب QR

از صفحه‌ی «چاپ برچسب QR» قطعات را انتخاب و چاپ کنید (۳ اندازه). QR فقط یک شناسه‌ی یکتا (`WH:XXXXXXXX`) است نه کد قطعه؛ پس اگر کد قطعه را ویرایش کنید برچسب‌های چاپ‌شده معتبر می‌مانند. اگر اسکن ممکن نبود، کد قطعه را می‌شود دستی (حتی با ارقام فارسی) وارد کرد.

## استفاده روی گوشی (مهم: HTTPS)

مرورگرها **فقط روی آدرس‌های امن** (`https://` یا `localhost`) اجازه‌ی دوربین می‌دهند. یعنی اگر گوشی‌ها با `http://192.168.x.x:3000` وارد شوند دوربین کار نمی‌کند (ثبت دستی کد کار می‌کند). سه راه:

1. **پیشنهادی:** نصب روی یک سرور/ویندوز با دامنه و گواهی معتبر، با Caddy یا Nginx به عنوان reverse proxy (و `TRUST_PROXY=1`). با این روش «نصب برنامه روی گوشی» هم بدون هشدار کار می‌کند.
2. گواهی خودامضا برای شبکه‌ی داخلی: `scripts/make-cert.ps1 -Ip <IP سرور>` سپس اجرای سرور با `SSL_PFX=data\server.pfx` و `SSL_PASSPHRASE=warehouse`. هر گوشی یک بار هشدار گواهی را تایید می‌کند (ممکن است امکان نصب PWA فعال نشود).
3. تونل (مثلاً Cloudflare Tunnel) برای ارائه‌ی HTTPS بدون باز کردن پورت.

نصب روی گوشی: Chrome › منو › «Add to Home screen» (یا «نصب برنامه»). در iPhone: Safari › Share › Add to Home Screen.

## خروجی‌ها

### ۱) خروجی کامل (Excel) — برای خود شما
از «گزارش‌ها و خروجی › خروجی کامل» (با بازه‌ی تاریخ شمسی). برگه‌ها:

| برگه | چه می‌بینید |
|---|---|
| **موجودی فعلی** | هر قطعه با موجودی، حداقل، کم‌موجود بودن |
| **ریز حرکات روزانه** | هر ورود و خروج، روز به روز و قطعه به قطعه: تاریخ، روز هفته، **ساعت اعمال** و **ساعت ثبت**، ورود/خروج، موجودی قبل و بعد، **ثبت‌کننده** و **تاییدکننده**، کارگر، علت، شماره سند، توضیح |
| **خلاصه روزانه قطعات** | برای هر قطعه در هر روز: موجودی اول روز، جمع ورود، جمع خروج، موجودی آخر روز، تعداد حرکت، اولین/آخرین ساعت، چه کسانی ثبت کردند، کدام کارگرها |
| **خلاصه روزانه کاربران** | فعالیت هر نفر در هر روز: اسناد ثبت‌شده، ردیف‌ها، جمع ورود/خروج، تعداد تاییدها و ردها |
| اسناد، گزارش ممیزی، اطلاعات گزارش | سربرگ اسناد، تغییرات سامانه، توضیح ستون‌ها |

«ساعت اعمال» لحظه‌ای است که موجودی واقعاً تغییر کرده (برای خروج‌های انباردار، لحظه‌ی تایید مدیر) و «ساعت ثبت» لحظه‌ی ثبت انباردار است. همه‌ی ساعت‌ها به وقت تهران و تاریخ‌ها شمسی هستند.

### ۲) فایل بارکد برای سپیدار
با سپیدار شما آزمایش شد: ورودی «بارکد» داخل سند (زیر جدول اقلام) فایل متنی را می‌خواند، **هر خط یک بارکد = یک واحد از آن کالا**. بارکد هر کالا همان **کد کالا** است (در کارت کالای سپیدار «بارکد کالا» را برابر کد کالا بگذارید).

- **برای یک سند:** در صفحه‌ی سند تاییدشده › «فایل بارکد سپیدار (TXT)». مثلاً ۳ عدد کد 31400 و ۲ عدد کد 32800 پنج خط می‌شود (نمونه: `samples/barcode-example.txt`).
- **برای چند سند:** «گزارش‌ها و خروجی › فایل بارکد سپیدار» برای هر نوع سند سپیدار (رسید: خرید داخلی/تولید/سایر؛ خروج: مصرف/فروش/سایر/انتقال بین انبار — برای هر انبار مقصد جدا) فایل می‌دهد و آن اسناد را «ارسال‌شده» علامت می‌زند؛ فایل‌های قبلی دوباره دانلود می‌شوند.
- **علت‌ها به نوع سند سپیدار:** ورود جدید/خرید ← خرید داخلی؛ بازگشت از کارگر ← تولید؛ سایر ورودی‌ها ← سایر؛ تحویل به کارگر ← مصرف؛ فروش ← فروش؛ سایر خروجی‌ها ← سایر؛ ضایعات (انبار 1004) و انتقال ← انتقال بین انبار.
- «موجودی اولیه» و «اصلاح شمارش» به سپیدار نمی‌روند.
- سپیدار سند خروج را که موجودی کالا را منفی کند نمی‌پذیرد؛ رسیدها را پیش از خروج‌های مربوط وارد کنید.
- هر خط یک واحد است؛ برای تعداد خیلی زیاد (بیش از ۵۰٬۰۰۰ برای یک کالا) فایل بریده می‌شود و هشدار می‌دهد.

### ۳) بسته‌ی «ساخت سند + بارکد» (اختیاری / آزمایشی — با برچسب زرد)

«الگوی دریافت» سپیدار هر ردیف را یک سند می‌سازد و سند بدون قلم نمی‌پذیرد، پس سند چندقلمی در یک مرحله ساخته نمی‌شود. این گزینه‌ی اختیاری یک **ZIP** می‌دهد:

1. `1-….xls` — سند را می‌سازد؛ فقط **قلم اول با تعداد کامل آن** (فهرست رسید/خروج › دریافت اطلاعات › الگوی دریافت). ستون‌ها همان ۱۱ فیلد الگوی خروج شما هستند (نوع قلم، شماره، تاریخ، کد انبار، کد تحویل‌گیرنده، کد انبار مقصد، نوع، ردیف، کد، واحد اصلی، کد حساب معین)؛ تاریخ به همان شکلی است که سپیدار می‌نویسد (`1405/07/19 12:00:00 ق.ظ`).
2. `2-….txt` — بارکدِ **بقیه‌ی اقلام**، هر واحد یک خط، برای ورودی «بارکد» داخل سند.
3. `0-راهنما-….txt` — مراحل همان سند.

شماره‌ی سند سپیدار و کد طرف حساب را خودتان می‌دهید (شماره‌ی موجود در همان انبار سند قبلی را بازنویسی می‌کند؛ سامانه شماره‌ی بعدی را پیشنهاد می‌دهد). هم برای هر سند (صفحه‌ی سند) و هم برای گروه اسناد (کارت فایل بارکد) هست. ترتیب فیلدهای «رسید» هنوز آزمایش نشده است. «چاپ برگه‌ی ثبت در سپیدار» در صفحه‌ی سند هم برای ثبت دستی هست.

## توسعه و تست

```bash
npm test
```

- بک‌اند: Node.js + Express + SQLite (`node:sqlite`) + ExcelJS؛ فرانت‌اند: جاوااسکریپت ساده (بدون build) با فونت وزیرمتن و اسکنر jsQR (همه‌چیز محلی است و به اینترنت نیاز ندارد).

- ساختار استقرار: `Dockerfile`, `docker-compose.prod.yml`, `Makefile`, `scripts/*.sh`, `deploy/nginx/app.conf.template`.

## نکات درباره‌ی داده‌ی اولیه (فایل Word)

این موارد هنگام وارد کردن اصلاح یا حدس زده شد؛ لطفاً بررسی کنید (از صفحه‌ی هر قطعه قابل ویرایش است):

- ردیف ۴ (رویه جارو): کد `3100` در فایل → `31000` (مطابق الگو).
- ردیف ۳۸ (لاستیک چرخ کوچک PVC): کد `34500` که با ردیف ۳۹ تکراری بود → `34400`.
- قطعاتی که «کد جدید» نداشتند با «کد قطعه» وارد شدند (مثلاً ۳۱۵، ۳۱۶، ۳۱۷).
- وزن‌های اعشاری مثل «۵/۱ گرم» به صورت ۱٫۵ تفسیر شد. جنس‌هایی مثل `EPOM`, `PUM`, `PPPP` همان‌طور که در فایل بود ماند.
